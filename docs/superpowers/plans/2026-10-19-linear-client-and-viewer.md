## Decisions

### From the spec and phase 0 (binding)

Spec sections 3–8 and 12; the phase 0 findings L1–L10 with their consequences; plan 1's Decisions 3–8 (`SyncProfile` holds pages and the incremental mode only; `BackendError`'s shape and texts; no `remedy()`; `BoardKey::Github(GithubBoard)`; `ContentRef.key: Option<String>`; `ViewFilter` from strings).

### Answered by Tyler (2026-10-19)

1. **Workspace views appear on Linear boards.** Shared custom views whose team is null are listed with the board's teams' views (`customViews(filter: { or: [team in board teams, team null] })`). `customView.issues` is ANDed with the board filter, so they show only that board's issues.
2. **Project-scoped views appear on project boards,** read through `Project.facets[].targetCustomView` in the resolve query. Tab order: built-in tabs, then the project's views, then team and workspace views.
3. **`issueSubGrouping` maps; `issueGrouping: assignee` does not.** Sub-grouping uses the same recognised set as grouping and becomes the board's swimlane (`View.group_by`). An `assignee` grouping is unrecognised and falls back (Status columns on a board, no grouping in a table).

### Plan-level decisions (flag any you disagree with before execution)

4. **One filter parser.** `model::filter::Filter` parses the GitHub-style syntax once. `column_constraint` becomes a thin wrapper over `Filter::constraint` and keeps every existing test; `still_matches` (GitHub's estimate) is left exactly as it is. On Linear boards the app uses `Filter::matches` and `Filter::constraint` directly.
5. **An unknown qualifier matches nothing** and is reported: the status line flashes `unknown filter field: <key>`. Silently ignoring a typo (`stauts:Todo`) would show every item and look like a working filter. `OR`, `AND` and parentheses are free text, as today's `column_constraint` already assumes.
6. **`ListQuery` replaces the view-id filter string.** `SyncJob::ViewIds`, `SyncEvent::ViewIds` and `Command::FetchViewIds` carry `ListQuery { filter: ViewFilter, include_archived: bool }` (memory: "`SyncJob::ViewIds` must carry the `ViewFilter`"). GitHub lists are `ListQuery { filter: Github(<view filter + f text>), include_archived: false }`, exactly today's string. Staleness compares `ListQuery`s.
7. **A Linear board's `ProjectId` is its canonical `BoardKey` string** (`linear:team:<uuid>`). Every `Syncer` method that takes a `ProjectId` keeps its signature; the Linear client parses the board back from it.
8. **An unknown total is 0.** Linear connections have no count, so the Linear client reports `Page.total = 0`. The UI reads 0 as unknown: "loading 300" instead of "loading 300/0", and "loaded 2000+ items (max_items)" / "loaded 2000+" when truncated (spec section 6). A GitHub total is 0 only on an empty board, which is never truncated, so GitHub text is unchanged.
9. **A board that no longer exists is forgotten, for both providers** (spec section 8; memory: "remember a board only after it resolves"). The board is remembered for the repository only after its first resolve succeeds, under the canonical key. A resolve failing with `BackendError::is_not_found()` forgets the repository's remembered board if it is that board, and opens the picker with "board not found: <board>". Today GitHub shows "could not load the board: …" on the status line and retries forever; This changes GitHub behaviour; approved by Tyler (2026-10-19).
10. **Wording changes (approved by Tyler, 2026-10-19):** the `f` help line "add a filter on top of the view's GitHub filter" becomes "add a filter on top of the view's own filter"; "View '<name>' layout changed on GitHub; local layout cleared" names the board's provider; the setup screen with no credentials at all lists the GitHub and the Linear fix (spec section 5, Credentials). GitHub's own setup texts are unchanged. Edit-only texts that say "GitHub" (`MAYBE_CREATED`, "GitHub returned an error", "Creating on GitHub…", `Denial::Creating`) stay: no Linear board can reach them in 0.4.
11. **`ProjectSummary` gains no fields.** Its provider and kind are already in `board` (`BoardKey::Github`, `LinearProject`, `LinearTeam`); `ProjectSummary::section()` derives the picker section. (The spec's "gains `provider` and `kind`", with less state to keep consistent.)
12. **Priority has four options.** Urgent, High, Medium, Low; priority 0 ("No priority") is no value, so the field's automatic "No Priority" bucket is the no-priority column and no pill is drawn. (The spec's five options would give two no-priority columns.)
13. **Manual order is a tie-break, not a field.** Linear's `sortOrder` is stored in `ContentFields.sort_order`; `sort_items` breaks ties with it when both items have one. A view ordered "manual" has no `SortSpec`, so its items follow `sortOrder`; "priority" sorts by the Priority field, then `sortOrder`. GitHub items have no `sort_order`, so their order is unchanged.
14. **Built-in tab filters are `IssueFilter` variables** built as `serde_json::Value` and sent with the generated operation's `QUERY` and `OPERATION_NAME` (finding L10). The generated `Variables` struct is not used for those operations, so no `null` key reaches the filter.
15. **The scrubber replaces people and the workspace, not every `name`.** The testbed's teams, states, labels, projects, cycles and views are seeded inventions; replacing them would break merged columns in replayed fixtures. The scrubber replaces `name`, `displayName`, `email` and `avatarUrl` inside user-like objects (an object with any of `displayName`, `email`, `avatarUrl`), the organization's `name`, and the workspace URL key in every string. (Spec section 10 says "every `name`"; this keeps its purpose, no real person in the repository.)
16. **Credentials resolve per provider at start and on `r`.** `LINEAR_API_KEY`, then `linear_api_key_command` run without a shell with a 20-second timeout (a dismissed Keychain prompt must not hang the pane). The setup screen appears only when neither provider has credentials.
17. **One backend per provider, chosen per job.** The runtime holds `Backends { github, linear }`; the controller tags each spawned job with the current board's provider; GitHub-only lookups always use GitHub. `Syncer::resolve` matches `(backend, board)` with explicit arms, no wildcard (memory).
18. **The incremental mode follows the board** (memory): `backend::profile_for(provider).incremental`, Linear `DateTime` (`updatedAt: { gt }`), GitHub `Date` as today.
19. **"Hide completed" views filter on the server.** A custom view with `showCompletedIssues: "none"` (finding L5) is `ViewFilter::LinearView { id, hide_closed: true }`, and its list request gets `{ state: { type: { nin: ["completed", "canceled", "duplicate"] } } }` ANDed into its `customView.issues` request. Other values ("all", null, anything unmeasured) show everything.
20. **Unmeasured view vocabulary is confirmed by recording.** Phase 0 measured `layout` (`board`, `list`), `issueGrouping` (`workflowState`, `priority`, `assignee`, `none`), `viewOrdering` (`priority`, `manual`) and `showCompletedIssues` (`all`, `none`). The plan assumes `project`, `cycle` and `label` (with `issueGroupingLabelGroupId`) for grouping, `createdAt`, `updatedAt` and `dueDate` for ordering, and `modelName` `"Issue"` for issue views. Task 13 records views set up that way and corrects the constants in `src/linear/views.rs` if Linear uses other strings.
21. **`runtime.rs:41` needs no log helper** (memory): it logs the Display of `event_loop`'s `anyhow::Error`, whose only sources are terminal, signal and editor errors; backend errors reach the UI as `SyncEvent::Failed` and the log as `error.kind()` only (`Syncer::fail`, `Syncer::mutate`).

### Task 1: The filter evaluator

**Files:**
- Modify: `src/model/filter.rs`

**Interfaces:**
- Consumes: `Field`, `FieldKind`, `Item`, `Item::field_value`, `Item::assignees`, `Item::labels`, `Item::ref_label`, `ContentState`, `Iteration` (all existing).
- Produces (`crate::model::filter`, re-exported from `model`):
  - `pub struct FilterContext<'a> { pub fields: &'a [Field], pub me: Option<&'a str>, pub today: Option<time::Date> }` — `me` is the viewer's user id, compared with `item.content_fields.assignee_ids` values.
  - `#[derive(Debug, Clone, PartialEq)] pub struct Filter` (private terms) with `pub fn parse(text: &str, fields: &[Field]) -> Filter`, `pub fn is_empty(&self) -> bool`, `pub fn unknown_keys(&self) -> &[String]` (lowercase, in typed order, deduplicated), `pub fn wants_archived(&self) -> bool`, `pub fn matches(&self, item: &Item, ctx: &FilterContext) -> bool`, `pub fn constraint(&self, field: &Field, ctx: &FilterContext) -> ColumnConstraint`.
  - `column_constraint(filter: &str, field: &Field) -> ColumnConstraint` keeps its signature and behaviour; `still_matches` is untouched (Decision 4).

The semantics (binding; terms are ANDed, a comma in values ORs them, `-` negates, keys and values are case-insensitive, a field key is its name or its name with spaces as hyphens):

| Term | An item matches when |
|---|---|
| free word or `"quoted phrase"` (also `OR`, `AND`, `(x`, `y)`) | its title or `ref_label()` contains it |
| `<single-select>:a,b` | its option's name is one of them |
| `<iteration>:a` | the iteration title is one of them; `@current` (start ≤ today < start + duration), `@next` (earliest start after today), `@previous` (latest whose end ≤ today); any `@` value matches nothing without `ctx.today` |
| `<number>:3`, `>3`, `>=3`, `<3`, `<=3`, `1..3` | its value compares so |
| `<date>:2026-10-01` and the same comparisons, `@today` | its date (the first 10 characters) compares so |
| `<text>:x` | its text contains `x` |
| `assignee:a` / `assignees:` | an assignee's name is one of them; `@me` when `ctx.me` is one of `assignee_ids`' values |
| `label:a` / `labels:` | a label's name is one of them |
| `is:open`, `is:closed` | its content state (an Issue or PullRequest); drafts are open |
| `is:issue`, `is:archived` | it is an issue; it is archived |
| `no:<key>`, `has:<key>` | it has no value, a value, for that field (`assignee`, `label` included) |
| an unknown key | never (Decision 5) |
| any item with `archived` | only if the filter has `is:archived`; a non-archived item never matches `is:archived` |

`constraint(field, ctx)` returns what `column_constraint` returns today for terms on `field`, except that `@current`, `@next` and `@previous` on an iteration field resolve to the matching iteration's title when `ctx.today` is set. `column_constraint(filter, field)` is `Filter::parse(filter, slice::from_ref(field)).constraint(field, &FilterContext { fields: slice::from_ref(field), me: None, today: None })`.
