# project-boards Linear Plan 3: Editing Linear Boards and 0.5.0

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.5.0: Linear project and team boards become editable through the existing keys, popovers and optimistic edits, with GitHub boards unchanged.

**Architecture:** Four PRs. PR A adds the seams with Linear still read-only: limits per provider in `SyncProfile`, capability sets per provider in `model::caps` (which also ends the `caps` → `backend` import), provider wording, the 0.4 leftovers and three new probes. PR B adds the write side below the UI: team ownership in the model with a resolver for team-owned values, Linear mutations in the client, the extra data some `Op`s carry, and the `Backend::Linear` arm of `ops::send`. PR C turns each Linear operation on in the UI, one capability at a time, then records fixtures and extends the live suite. PR D is the release.

**Tech Stack:** Rust 2024 (MSRV 1.88), tokio, reqwest 0.13, graphql_client 0.16 (validation; Linear requests sent raw with the generated `QUERY` and `OPERATION_NAME`), serde_json, ratatui 0.30, thiserror 2, time 0.3, wiremock, insta, tempfile. No new dependencies (the UUID comes from `/dev/urandom`, Decision 6).

**Spec:** `docs/superpowers/specs/2026-10-20-linear-editing-design.md` (read all of it). It builds on `docs/superpowers/specs/2026-10-15-linear-adapter-design.md` (the Linear spec) and the main spec `docs/superpowers/specs/2026-09-30-project-boards-design.md`, which still governs GitHub. Measured facts: `docs/phase0-findings.md`, section "Linear". Conventions follow plan 2, `docs/superpowers/plans/2026-10-19-linear-client-and-viewer.md` (read its Global Constraints and Executing this plan).

**Out of scope:** everything in the spec's section 2 "Out of scope for 0.5", and the deferred leftovers in its section 11.

### Plan-level decisions (flag any you disagree with before execution)

1. **Capability sets live in `model::caps`.** `ProviderCaps` and `provider_caps(Provider)` replace `backend::read_only_reason` in `caps` and `chrome`, which ends the layering leftover. Linear's `ops` list starts empty (read-only, the 0.4 text) and grows task by task in PR C, so every merge of `main` ships either a working Linear operation or the 0.4 refusal, never a half-wired one.
2. **Team ownership lives in `LinearMeta`, not on options.** `LinearMeta` gains `teams: Vec<TeamMeta>` and `owners: BTreeMap<String, String>` (state, cycle or label-group id → team id), both `serde(default)`. An issue's team comes from `ContentRef.container` (its team key, 0.4). `SelectOption`, `Iteration`, `Field` and `ContentFields` gain nothing, so no GitHub struct literal changes. A Linear board cached by 0.4 has empty `teams`: team-owned edits get `NeedsRefresh` until the first resolve (spec section 6).
3. **One resolver, in `model::teams`.** Every UI path that sets a value on a Linear issue (moves, `e`, close and reopen, presets for new and existing issues) asks `model::teams` for that issue's team's value, and shows its `TeamRefusal` message when there is none. On a GitHub project every resolver call returns the value unchanged.
4. **`Op` gains Linear data only where `send` cannot work without it:** `Reorder.sort_order: Option<f64>`, `Comment.client_id: Option<String>`, a new variant `Op::GroupLabel` for single-select label groups (it carries the label it replaces), and two new `NewItem` variants (`LinearIssue`, `LinearExisting`). GitHub builds `None` or never builds the new variants. Close and reopen on Linear are sent as `Op::SetField` on `linear:status` (spec section 7).
5. **`Op::apply` sets the content state from an option's kind.** When `SetField` sets a single-select option whose `kind` is `Some`, `apply` sets the item's `ContentState` and `StateReason` by the Linear spec's section 4 table, so a card moved to Done (or closed with `X`) shows closed at once. GitHub options have `kind: None`, so GitHub is unchanged.
6. **The UUID v4 comes from `/dev/urandom`** (`crate::uuid::new_v4() -> std::io::Result<String>`), on both supported platforms, with no new dependency (spec section 16 leaves this to the plan).
7. **Archive and unarchive confirm with `Confirmed::Item`** (the payload's `entity`), falling back to `Applied` when it is null. Title, body, field edits, remove and existing-issue adds confirm with `Item`; comments with `Applied` (the detail reloads, as today).
8. **`FORBIDDEN` keeps today's mapping** (`MissingPermission { provider: Linear, needed: [] }`, in `execute_linear`), whose toast text is that variant's Linear Display. The spec asks for Linear's own message; the transport drops it on purpose and L13 has not shown what it says. Task 5 records the message; if it is worth showing, Task 7 carries it (in a way Tyler approves, since it touches `BackendError`).
9. **A skipped preset on an existing issue is said at submit time:** the status line reads `<reason>; adding TBA-12 without it`, and the add is sent. (The spec's toast wording `added TBA-12; …` would need a fake `BackendError` in `Confirmed::Created.refused`.)
10. **Probes are selected with `PB_PROBES`.** `examples/probe_linear.rs` runs L1–L9 as today when `PB_PROBES` is unset, and only the named steps (`l11,l12,l13`) when it is set, so the new write probes never run by accident.
11. **Team candidates are a Linear twin of repository candidates,** not a generalisation of the `RepoSlug` key: `App.team_candidates: HashMap<String, Lookup<TeamCandidates>>`, its own `Command`, `SyncJob`, `SyncEvent` and `SyncTask` variants. The checklist popups carry a `CandidateSource` so one fill path serves both.

## Review Focus

The five inputs or conditions the spec implies but no feature test exercises, most likely to bite first. Each has a test in the task named.

1. **A Linear board painted from a 0.4 cache** (no team data yet): team-owned edits (status, cycle, team label groups, close, reopen, new issues) say "refresh with r" instead of sending another team's id; priority, title and comments work; after the resolve everything works. Task 9: `a_cached_04_board_refuses_team_owned_edits_until_resolved`.
2. **A lost answer on a Linear create, then `R`:** the retry carries the same UUID; a "duplicate id" answer becomes a created issue; no second issue. Task 8: `a_resent_create_carries_the_same_id_and_a_duplicate_answer_is_created`; Task 14: `r_resends_a_lost_linear_create`.
3. **An issue whose team is not one of the board's teams** (moved to another team in Linear's app): team-owned edits refuse with "refresh with r"; nothing with another team's id is sent. Task 6: `an_issue_of_an_unknown_team_needs_refresh`.
4. **Neighbours with equal or missing `sortOrder`, or no float between them:** the reorder is refused and nothing is sent. Task 11: `reorder_between_equal_neighbours_is_refused_and_sends_nothing`.
5. **A key that may not edit one team (FORBIDDEN):** that edit is undone with a reason; the next edit, to another team's issue, is still sent. Task 9: `a_forbidden_edit_is_undone_and_later_edits_still_go`.
